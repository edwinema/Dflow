# R2 P1 修复

- 业务角色通过显式 `apiRoles` 配置 editor（业务编制与送审）或 auditor（审核能力），不从角色名称、菜单名称或“全部菜单”推导后台写权限。系统管理员能力仅保留已有直接账号授权，不能通过业务角色取得。
- 启用的业务角色能力在每次认证、写事务内重新计算；删除或停用角色、移除能力后立即撤权。角色权限页展示并保存实际能力，首次加载选中真实角色。
- 流程编制写入必须由 admin，或具备 editor 能力且为该流程责任人/协作者。保存 XML、元数据、发布送审、废止申请、附件和协作配置执行对象校验。协作者不能自行增加协作者或变更责任人；责任人变更必须匹配唯一启用用户。客户端不能伪造 canEdit。
- 流程响应携带服务端 canEdit/canDirectPublish，编制页面隐藏不可用的画板/送审/直接发布按钮；入口另有权限提示。直接发布仍要求审核能力，不随编制角色自动授予。
- 新制度/风险的申请人 ID 与名称由服务端写入，修订、重新送审同样更新。历史记录兼容 applicant/申请人显示名字段；列表与详情使用同一投影和缺失文案，不按当前审批人推测申请人。
- 制度状态中的 JSX 字面量美元符已移除，显示为“待第1级 (审批人)”。

线上角色能力启用单独进行：对“流程管理员”增加 editor 和流程编制/制度/权责菜单，不更改账号系统管理员权限、不更改既有流程责任人。需记录操作前角色配置并通过管理员 API 更新，保留审计日志。
